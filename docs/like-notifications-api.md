# 投稿・いいね通知API

[PR #60](https://github.com/jphacks/tkb_2605/pull/60)のviews / serializers / repositoriesを基準とし、#58・#59の通知保存・表示・投稿詳細を統合する。投稿処理を別実装へ置き換えず、いいねは追加のみの仕様を維持する。

## 投稿といいね

- GET /api/posts/ と GET /api/users/{user_id}/posts/ はDBの投稿をページングして返す。
- POST /api/posts/ は201。post_type=1は本文必須、2は本人のworkout_id必須で本文省略可、3は本文を空にする。本文上限は500文字。
- GET /api/posts/{post_id}/ は通知から開く詳細用。不存在・不正なUUIDは404。
- PUT /api/posts/{post_id}/like/ は本文なしで追加。再送も200、is_liked=true、件数は増えない。DELETEやトグルによる取り消しは提供しない。
- 全操作にセッション認証、書き込みにCSRFが必要。投稿者・実行者はリクエスト本文から受け取らない。

## 通知

初回のいいね保存と通知保存を単一トランザクションで行う。投稿の行ロックといいねの一意制約で重複を防止する。自分の投稿、無効・存在しない投稿者へのいいねでは通知しない。既存のいいねを再送しても過去の通知は生成しない。

GET /api/notify/ は全員向けの開始通知とログイン中のユーザー宛のいいね通知だけを返す。開始通知の従来4項目は変更しない。いいね通知にはnotification_type=post_liked、post_id、post_excerpt（本文先頭100文字）を加える。投稿削除時は関連通知も削除する。フロントからいいね時にPOST /api/notify/を送信する必要はない。

取得位置・件数上限は既存の消費型通知APIを維持する。取得済み通知は再取得できず、上限超過や受信途中の通信失敗の再配信もない。フロントは現在のセッション中に受信した最大100件を保持する。Web Push配送は別途バックエンド実装が必要で、この変更だけでは実現しない。

## DB移行

デプロイ前にSQLiteのバックアップを取得し、通常のmanage.py migrateを実行する。posts.0002は同じ投稿・ユーザーの重複Likeを最小IDの1件にまとめてから一意制約を追加する。通知の後付け生成はしない。notifications.0003は種別・宛先・投稿参照と制約を追加し、既存通知を全員向けのworkout_startedとして保持する。DB初期化は不要。

## 検証

バックエンドのposts / notificationsテストで認証・CSRF・他人の記録添付拒否・通知先分離・再送・自己いいね・失敗時ロールバック・一意制約・削除時連動を確認する。フロントではAPI契約、500文字、本文なし記録共有、いいねから開始通知を送らないこと、通知リンクと取得差分の保持を検証する。
