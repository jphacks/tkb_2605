# 通知とホームの表示

ホームの見出しはTIMELINE、タブは「マスメイト」とベルの2つ。投稿は既存のGET一覧を表示し、フォロー中／フォロワーの分類と解除操作を設けない。タブ切替で投稿・ページング・いいね状態を失わない。

## 開始通知

ホームの「トレーニングを開始」で記録のPOSTが成功したら、ボディなしの `POST /api/notify/` を一度呼ぶ。おすすめから初めて種目を選んで記録を作る場合も同様。既存記録への種目追加では送らない。連打をまとめ、記録の作成失敗時・ログアウト・アカウント変更後には通知を送らない。通知単独の送信ボタンは置かない。

送信失敗はアプリに表示し、記録への遷移は続ける。送信結果が不明な場合の自動再送はしない。送信した通知をフロントで受信履歴へ捏造しない。バックエンドが保存した履歴を `GET /api/notify/?limit=100` で表示する。

## 受信履歴

- トレーニング開始: 「〇〇さんがトレーニングを開始しました。」
- 投稿へのいいね: 「〇〇さんが『投稿』にいいねしました。」対象投稿へリンクする。
- 通知種別の選択、一覧の絞り込み、アプリ内オンオフ設定は置かない。GETで返った2種類の履歴をすべて表示する。
- 初回・15秒ごと・画面復帰時・Web Push受信時に取得。初回は履歴、その後の新IDは新着表示。日時順・ID重複排除、取得失敗時の一覧保持を維持する。「新着の表示をクリア」は履歴を削除せず、この利用中の印だけを消す。
- GETは最新100件まで。サーバーの既読更新・ページング仕様は未定義。

## いいね通知の未確定項目

Issue #42の現時点のレスポンスは `notification_id, notifier_id, notifier_name, notified_at` の4項目だけ。これは開始通知として引き続き受理する。いいねを区別する項目と投稿IDはまだ公開仕様にないため、**以下は提案中のフロント接続契約**。確定した仕様が異なる場合はAPIアダプターを調整する。

```json
{
  "notification_id": 2,
  "notification_type": "post_liked",
  "notifier_id": 3,
  "notifier_name": "たろう",
  "notified_at": "2026-10-25T12:00:00+09:00",
  "post_id": "post-uuid",
  "post_excerpt": "今日のトレーニング"
}
```

`notification_type` は省略または `workout_started` が開始通知、`post_liked` がいいね。いいねでは空でない文字列の `post_id` が必須。`post_excerpt` は任意。投稿者・通知先の決定といいね時の通知保存はバックエンドが行う。フロントの「いいね」から全員向けの開始通知APIを呼ぶことはしない。

## Web Push

端末／ブラウザーの通知許可だけをオンオフの基準とする。アプリ独自の通知設定・種類別購読・解除ボタンはない。初回のトレーニング開始操作でブラウザー標準の許可を求め、許可済みならアプリ利用開始・画面復帰時に購読を同期する。拒否してもGETの履歴は表示する。OSの許可や配信制約をフロントから上書きできず、すべての端末への必着を保証するものではない。

プッシュ配送・端末登録APIはまだバックエンド側の接続が必要。[Web Pushの契約](web-push.md)を参照。認証済みセッションでのみ取得・送信し、ユーザー変更時は通知ストアを作り直す。
