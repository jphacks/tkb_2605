# 通知APIの接続

[Issue #42](https://github.com/jphacks/tkb_2605/issues/42) の通知専用APIを使用する。`post_type: 3` の投稿APIとは独立している。バックエンドのモデル、通知先の決定、保存、配送処理は変更しない。

| 操作 | リクエスト | 成功応答 |
| --- | --- | --- |
| 通知一覧 | `GET /api/notify/?limit=100`（ボディなし） | HTTP 200、通知オブジェクトの配列 |
| 全員への筋トレ通知 | `POST /api/notify/`（ボディなし） | HTTP 200。ボディの形式は未定義なのでJSONを必須にしない |

一覧は `notification_id`、`notifier_id`（正の整数）、`notifier_name`（空でない文字列）、`notified_at`（タイムゾーン付き日時）を検証する。通知IDで重複を取り除き、通知日時の降順で表示する。受信者の選別はバックエンドが行い、フロントはサーバーの一覧に返った通知を表示する。

## 取得と新着のお知らせ

- 現在の認証ガード内でアプリを利用している間、通知一覧を1か所で共有する。画面・投稿ダイアログを移動しても取得処理を重複させない。
- 初回と前の取得完了から15秒後にGETする。非表示・オフライン中は次の定期取得を止め、表示復帰・フォーカス・オンライン復帰で直ちに取得する。通信は10秒でタイムアウトし、同時の更新要求は1リクエストにまとめる。
- 初回成功時は履歴を表示するだけで、新着のお知らせは出さない。その後、未取得の通知IDが現れたら、アプリ内バナー、ホームのベル・サイドメニュー・通知タブの件数、通知行の「新着」を更新する。
- `/notifications` とホームの通知タブは同じ一覧を表示する。「新着の表示をクリア」はこの利用中のローカル表示だけを変更する。サーバーの既読APIや既読状態は未定義のため、既読更新を送信しない。
- 通知先プロフィールへのリンクには応答の `notifier_id` を使用する。プロフィールAPIは既存の未接続範囲であり、対象の情報がない場合は既存の準備中表示となる。
- 取得失敗時は最後の成功一覧と新着表示を残し、エラーと再試行を表示する。初回失敗を「通知なし」と表示しない。HTTP 401/403はログイン確認、404/501は未接続と案内する。
- プレビュー終了時に通信を中断して状態を破棄する。遅れて返る応答を次の利用に反映しない。localStorageやsessionStorageには保存しない。

## 送信

通知画面の「全員に筋トレ通知を送る」でのみPOSTする。画面表示・トレーニング開始・通常の投稿で暗黙に送信しない。送信中の連打をまとめ、ネットワーク障害やサーバーエラーで自動再送しない。結果が不明な場合は、既に届いた可能性を案内する。HTTP 200では「通知の送信を受け付けました」と表示し、受信一覧への追加はGET結果に従う。

同一オリジンのCookieを使用し、POSTはDjangoの`csrftoken` Cookieが存在するときに`X-CSRFToken`ヘッダーを付ける。送信者ID・受信者IDをフロントで捏造しない。

## 現時点の境界と検証

- 現在のmainには通知エンドポイントの内部実装がない。仕様どおりのHTTP応答を返すローカル模擬APIで、送信・受信・新着表示・失敗からの復帰を検証する。実ユーザーへの配送を確認したものではない。
- 本番のログインガードは維持する。認証APIが接続されるまでは開発用「画面をプレビュー」から確認する。将来の認証セッション接続時には、`App.tsx`のアクセス許可と通知Providerの`enabled`を同じセッション状態に結び付ける。
- これはアプリ内通知。アプリを閉じた状態や非表示中のOSプッシュ通知、SSE/WebSocket、購読登録は仕様にないため実装しない。
- GETの`limit`上限は100で、offset/cursorはない。表示は最新100件であり、非表示中などに100件を超えて届いた通知の全件追跡は保証しない。
- `npm test`でAPI契約・重複・新着検出・エラー保持・送信連打・終了後の応答・定期取得の停止/復帰を検証する。`npm run lint`と`npm run build`も実行する。
