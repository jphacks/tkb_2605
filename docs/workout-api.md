# DB版記録APIへのフロント接続

PR #44（main c08aaf5）のnote/views.py、serializers.py、repositories.pyに合わせる。URLは変更されておらず、/api/workouts/と/api/workout-exercises/を使う。/note/を加えたり、別の未定義エンドポイントへ変更したりしない。

- 開始POST {} → 201。サーバーのUUIDと日時を使用する。
- 種目追加POST {exercise_id} → 201。選択したUUIDと返されたexercise_idの一致を確認し、サーバーが発行したworkout_exercise_idで記録画面を開く。
- セットPOST {sets:[{set_number,reps,weight}]} → 201。全件置換。回数・番号は正整数、重量は0〜99999.9の小数第1位までの文字列。戻り値が送信した各セットと一致し、ID・番号が重複せず順序どおりであることを確認する。
- 詳細GET → 200。DB保存済みのセットを復元する。キャッシュを避け、通信を10秒でタイムアウトする。
- 終了PATCH {is_completed:true} → 200。終了済みのGET結果は読み取り専用にし、結果画面にも終了状態を反映する。未終了の結果画面からは「記録を続ける」へ戻り、共有は終了済みの記録のみ許可する。

PR #62以降、詳細GETは認証済みの他ユーザーにも公開する。開始・種目追加・セット保存・終了の書き込みは引き続き本人の記録だけに許可する。CIのリポジトリ層テストも、他ユーザーの詳細取得成功と書き込み拒否をそれぞれ確認する。

同一オリジンのDjangoセッションCookieとcsrftoken/X-CSRFTokenを使用する。ユーザーIDを送信本文へ追加しない。認証ガード・DEVプレビューは維持し、専用ログインの実装は行わない。403はログイン／CSRF確認、404は記録・種目・書き込み時の所有者確認、409は終了済みとして案内する。

## 結果の共有

共有ダイアログの本文には、詳細GETで取得済みの種目名・セット数・各セットの番号、重量、回数をテキストで展開する。未記録の種目は含めない。投稿APIには編集後の本文を `content`、元の記録を `workout_id`、`post_type: 2` として送る。記録IDとプレビューだけの送信にしない。

ダイアログをURLから直接開いた場合も詳細GETで本文を復元する。取得中・取得失敗・未終了・セットなしでは投稿できず、取得失敗には再試行を表示する。本文全体が500文字を超える場合は切り捨てず、文字数を表示して編集を促す。

## 保存とエラー

セット送信成功後に終了PATCHだけ失敗した場合、同じ画面での再操作はPATCHのみ。セットのPOSTを重複しない。通信・応答不正・5xxなどで書き込み結果が不明な場合は、GETで保存内容を確認する。入力と一致するセットまたは完了状態を取得できた場合だけ成功として扱う。GETが失敗したり内容が違ったりした場合はエラーを残す。書き込みの自動再送はしない。

新規記録と種目追加には重複防止キー／一覧APIがない。通信エラー後に再度開始すると別の記録が作られ得るため、保存済みの可能性を案内する。入力は画面内だけで、再読み込みではサーバーから復元する。古いlocalStorageの下書きを移行・送信しない。

## 検証

- フロントの単体テスト、lint、ビルド。
- 独立したSQLiteと検証用ユーザーを用意し、フロントの実APIクライアントから開始→種目追加→セット保存→全件置換→終了→GETを実行。UUID・内容・終了状態を確認。
- 完了後書き込み409、未認証GET403も確認。
- ブラウザーではローカル検証用セッションアダプターを経由し、スクワットを選択、55.5kg×8回と50kg×10回を保存・終了・結果表示。再表示でも保存内容が復元されることを確認。
- 認証画面との本番統合、実利用者のデータは検証対象外。バックエンド・migration・composeは変更しない。
